# Устройство версии 1.3.0

MRA готовит ответы, которые проверяет оператор. SQLite хранит входящие обращения, материалы, черновики, происхождение ответа и очередь HOLD.

## Поток

1. `import-json` или `import-legacy` принимает обращения. Идентичность: площадка + кабинет + тип + внешний ID. SKU Ozon разрешается через карту конкретного кабинета.
2. Обращение имеет числовую ревизию. Изменение текста, плюсов, минусов, оценки или товара увеличивает её и отменяет прежний HOLD.
3. Обработчик атомарно получает токен захвата. Второй обработчик не вызывает модель для того же обращения. Сетевой вызов выполняется за пределами транзакции SQLite.
4. Перед вызовом проверяются контрольная сумма утверждённого материала и доступность правил. После вызова повторно проверяются токен, ревизия и источники.
5. Строгое решение модели либо создаёт черновик, либо передаёт обращение оператору. Сбой связи, неполный ответ и ошибка JSON не создают покупательский текст.
6. Черновик, состояние и журнал записываются одной транзакцией. При ошибке записи операция откатывается; остаётся состояние для явного повтора.
7. `approve` проверяет актуальность входа, правил и материала и одной транзакцией сохраняет одобрение, журнал обработки и `held`.

## Источники и ограничения

Контрольная сумма фиксирует целостность и происхождение импорта; она не является цифровой подписью владельца. При миграции старые контрольные суммы проверяются по прежнему формату, новые используют канонический JSON.

Ссылки `used` проверяются на существование строк материала. Они не доказывают смысловую истинность каждого утверждения; ответ проверяет оператор. Регулярные выражения в `anonymize.py` скрывают очевидные контакты, но не обеспечивают полное удаление любых персональных данных.

Каталоги и входящие вопросы/отзывы читаются напрямую из API WB/Ozon/Яндекс. JSON и read-only SQLite предыдущего коллектора остаются дополнительными способами импорта. communication-клиент сохраняет исходное назначение и отпечаток обращения. delivery-preview привязывает одобренный черновик к этому назначению и ревизии; deliver сначала перечитывает вопрос и ответы, затем явно отправляет и сверяет результат. Подробные контракты: [CONNECTORS.md](CONNECTORS.md), эксплуатация: [OPERATIONS.md](OPERATIONS.md).

catalog_accounts и catalog_listings хранят отдельные матрицы кабинетов. catalog_aliases разделяет типы внешних ID; пустой article означает неоднозначность. catalog_runs хранит все попытки, включая неудачные. Только полностью прочитанный снимок меняет текущий каталог. message_inputs сохраняет hints, чтобы изменение связей пересопоставляло обращения и отменяло устаревшие черновики.

audit_events содержит время и тип события, audit_documents — дедуплицированные JSON-снимки. review_events связывает оператора, действие и версии черновика. Ручное решение и изменение состояния фиксируются одной транзакцией; запись о запросе действия и сбое остаётся после отката. Подробный контракт: [AUDIT.md](AUDIT.md).

## Комплектные знания

В knowledge/ поставляются действующие правила v2.1, неизменённый Markdown-канон и очищенная карта Ozon. `mra/knowledge.py` проверяет SHA-256, выделяет разделы по артикулам и переносит их текст в SQLite без генерации или пересказа. Для каждого раздела сохраняются исходные номера строк.

`build_payload` является общим сборщиком запроса для preview и живого вызова. Preview не содержит ключа и не выполняет HTTP. Doctor сверяет не только контрольную сумму базы, но и подключение всех комплектных карточек и связей.

Режим человека в петле на время теста и последующий фоновый режим зафиксированы в ACCEPTANCE.md. Отправка реализована отдельным действием; HOLD не выдаётся за отправленный ответ. Схема SQLite 5 добавляет remote_inputs и delivery_jobs, сохраняя журнал и прежние черновики. Устойчивый признак начала записи исключает слепой повтор после сбоя; восстановление неопределённого результата выполняет только чтение. Натурная приёмка отдельно описана в FIELD_TEST.md.

Лимиты всех клиентов: mra/rate_limits.py, схема SQLite 6; [политики](RATE_LIMITS.md). Локальная настройка следующего оператора: mra-setup.command и tools/configure.py, параметры провайдера — data/runtime.json без секретов.


## Автономный режим и первый запуск

Самостоятельная фоновая работа и допуск к автопубликации описаны в [AUTONOMOUS_MODE](AUTONOMOUS_MODE.md): текущие компоненты, план работы без терминала, постепенное включение по кабинетам/категориям, исключения и оставшиеся задачи. Фоновый авторежим пока не реализован и не включён.

Для первого запуска используйте **start.command**: кабинет → провайдер → заполнение файлов в private/credentials → локальная проверка и проверка API → СТАРТ. Инструкция: [START_HERE](START_HERE.md). Папка private/ игнорируется Git.
