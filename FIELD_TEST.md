# Проверка с человеком в петле

Участники: оператор, проверяющий ответ коллега и при необходимости наблюдатель в кабинете. Реальную отправку подтверждает оператор, видящий точный вопрос, текст ответа и кабинет.

Первый подтверждённый кабинет — **Ozon Deppa MSK**. Код кабинета: acct_deppa_ozon_msk. Важное уточнение: исходный пилот планировался на Deppa, но предоставленный владельцем ключ относится к Deppa MSK; реальные успешные публикации выполнены именно там.

После установки по START_HERE.md запускайте рабочую сессию с явным кабинетом и категорией. Для проверенного сценария выбраны наушники с материалом в каноне. На экране сразу вопрос и готовый ответ.

- **Да** одобряет точный показанный вариант, выполняет проверки перед записью, отправляет ответ и читает результат.
- **Нет** отклоняет вариант без отправки и продолжает сессию со следующим вопросом.
- **Переделать** запрашивает замечание оператора отдельной строкой. Один новый запрос модели получает вопрос, прежний ответ, замечание, правила и материал артикула. Новый вариант нужно принять заново.

По ошибке API или отсутствию надёжных данных автоматического повтора нет. Если модель передаёт вопрос оператору из-за недостатка фактов, текущая сессия останавливается. Это отдельная доработка поведения очереди, перечисленная в статусе передачи.

Проверьте: факты ответа соответствуют канону; кабинет выбран верно; после Да API принял ответ; после модерации текст виден; повтор того же задания не создаёт дубль; после Нет вопрос не отправлен; после Переделать старый и новый варианты и замечание присутствуют в журнале.

Статус accepted означает принятие запроса API, observed — чтение текста без подтверждения публикации, published — подтверждение публикации площадкой. После неоднозначного сбоя используйте delivery-reconcile, а не новую отправку.

Команды проверки:

```bash
./mra-cli doctor
./mra-cli readiness
./mra-cli delivery-status
./mra-cli trace MESSAGE_ID --full
./mra-cli backup data/after-field-test.sqlite3
```
