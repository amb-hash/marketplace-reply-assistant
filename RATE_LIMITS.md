# Ограничение запросов площадок

Все реальные запросы каталога, вопросов, отзывов, отправки и проверки ответа проходят AccountLimiter в mra/rate_limits.py. Состояние хранится в той же SQLite, что обращения. Политика метода и общая квота кабинета резервируются одной транзакцией BEGIN IMMEDIATE. Отказ одной квоты не расходует другую. В каждый момент выполняется не более одного запроса на кабинет; конкурентный процесс получает понятную причину остановки.

| Маршруты | Политика MRA |
|---|---|
| WB, вопросы и отзывы, персональный/сервисный/базовый с секретом | Общая категория: до 3 запросов за скользящую секунду, интервал не менее 0,4 с |
| WB, базовый или неизвестный тип | До 5 запросов за скользящий час, интервал 720,1 с. Для регулярной работы выберите подходящий токен |
| WB, каталог | Локальный потолок 50 запросов за минуту, интервал 1,1 с |
| Ozon | Локальный потолок 50 запросов за минуту на кабинет и метод, интервал 1,1 с; это настройка MRA, а не утверждение об официальной квоте конкретного метода |
| Яндекс, чтение вопросов/ответов/отзывов | До 1000 запросов на метод за скользящий час, интервал 3,7 с |
| Яндекс, создание ответа | До 500 запросов на метод за скользящий час, интервал 7,3 с |
| Яндекс, каталог | До 50 запросов за минуту, интервал 1,1 с |

Дополнительно общий локальный потолок — 50 запросов за минуту на кабинет. Расширенные подписочные квоты не используются. WB не использует разрешённый всплеск для ускорения. В Ozon алиасы объединяются по Client-Id, в Яндексе при явно заданном business_id — по нему. Если business_id определяется автоматически, используйте один локальный account_id на кабинет и затем сохраните найденный business_id в настройках.

Короткое ожидание до 30 секунд происходит перед новым запросом. При долгом ожидании, активном чужом запросе или сохранённом cooldown действие останавливается до сети. Захват имеет срок 120 секунд с учётом запланированного ожидания; после аварии процесс не оставляет вечную блокировку. HTTP timeout — 45 секунд.

При 429 и яндексовом 420 сохраняется пауза: 15 минут при первом ограничении, затем 30, 60, 120 и максимум 240 минут для последующих ограничений без успешного запроса. Если Retry-After или X-Ratelimit-Retry требуют дольше — соблюдается более длинный срок. Учитывается Retry-After в секундах и формате HTTP-date. Успешный ответ сбрасывает счётчик последовательных ограничений. Остаток 0 в X-RateLimit-Resource-Remaining Яндекса или X-Ratelimit-Remaining WB блокирует следующие запросы до указанного сервером восстановления. Длинные паузы не скрываются внутри автоматического повтора.

Между процессами, использующими одну SQLite, квоты общие. Перезапуск терминала не снимает cooldown. Отдельная установка и стороннее приложение могут расходовать квоту того же продавца независимо; MRA реагирует на серверные ограничения и не обещает исключить любой 429. Собственная блокировка не координирует независимые копии БД.

Резервирование, ожидание, результаты API и назначенная пауза сохраняются в журнале. Текущее состояние видно в `./mra-cli readiness`. Счётчики запросов за последние сутки — техническое окно лимитера; полный журнал действий хранится отдельно и не очищается этим окном. Повтор ответа после неоднозначной записи запрещён независимо от состояния лимитера.
